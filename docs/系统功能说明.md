# 系统功能说明

团校积分系统的完整功能说明（面向开发者与系统管理员）。本文档对应 v3.0 工程化重构后的
当前实现，细节一律以代码为准：后端 `backend/`（Flask + Blueprint 拆分 + SQLAlchemy 2 +
SQLite），前端 `frontend/`（React 19 + TypeScript + Vite + Tailwind CSS 4，生产模式由
Flask 直接托管 `frontend/dist` 并做 SPA fallback）。

## 一、核心功能

### 1.1 学生端

- 登录 / 注册：注册前须先通过学号邮箱获取验证码；注册成功后立即弹窗绑定动态验证码
  （OTP）。忘记密码通过邮箱验证码 + 自设新密码重置。
- 查看个人学分：总学分、各学分类别得分与达标状态、条目到类别的智能分配结果。
- 查看活动列表（按学分类别分组）。
- 活动报名：浏览进行中的问卷、提交报名、修改报名、取消报名、现场签到（一次性签到码）。
- 报名信息维护（`/student/profile`）：手机号、微信号、建议，直接存放在学生档案中。
- 反馈：提交/修改 BUG 反馈；集中活动反馈开启期间提交活动漏录申请，查看处理状态与回复。
- 账号安全：修改密码、主动重置 OTP（扫码 + 验证码确认才生效）。
- 导出自己的学分报告 PDF（前端生成）。

### 1.2 管理员端（部门普通管理员，role=admin）

- 学生查看：可查看学生列表（学号、姓名）；联系方式、报名详情与 OTP 状态仅系统管理员可见。
- 活动管理：在其有编辑权限的活动内创建记录、录入/批量录入/批量修改/批量删除学分条目。
- 问卷管理：为其可编辑的活动创建报名问卷、查看填写记录、导出、现场签到管理
  （开启/关闭签到、确认/代签、生成签到码、取消签到、缺席标记与候补转正）。
- 数据报表：学分统计总览（类别达标率、总分分布、最终合格率等）。
- 反馈处理：回复 BUG 反馈；核定/拒绝/重新打开活动漏录申请；开启/关闭集中活动反馈。
- 系统设置查看：类别列表（增删改仅系统管理员）、部门列表。

### 1.3 系统管理员（内置唯一 system 账号）

在普通管理员能力之上：

- 学生管理完整权限：添加/修改/删除学生、批量导入（CSV）、修改学生密码、编辑学生报名信息、
  导出报名信息的 xlsx、重置学生 OTP（下次登录自动邮件重绑）。
- 类别设置：创建/修改所需学分/删除学分类别；设置总学分要求（Setting 键
  `total_required_credits`）。
- 部门管理：添加/删除部门。
- 管理员账号管理：创建普通管理员（创建时一次性返回 OTP 二维码与密钥）、修改密码/部门、
  删除管理员（清理其活动编辑授权，创建的活动转为无属主）、重置管理员 OTP（两步确认）。
- 查询任意学生学分（`/api/query/student`）、全体学生学分汇总、导出学生学分统计 xlsx、
  导出全部问卷填写记录 xlsx。
- 创建独立问卷（不绑定活动的问卷仅系统管理员可创建/管理）。

system 账号本身不允许通过任何 Web 接口创建、删除或修改（密码与 OTP 只能在本机维护页操作）；
接口也不允许创建或提升第二个 `system_admin`。

### 1.4 本机维护台 `http://localhost:5002/local/system`（独立端口，仅绑定回环，主应用不挂载）

集中维护三类只允许出现在本机的敏感信息（Web 管理后台不提供任何入口）：

- system 登录密码：可自定义（至少 8 位）或留空随机生成，结果仅显示一次。
- system OTP：两步绑定——生成候选二维码，扫码并输入 6 位验证码确认后才生效；放弃则原 OTP 不变。
- 邮件服务配置：SMTP 服务邮箱、密码/授权码（Fernet 加密存储）、学生邮箱后缀，以及测试发送
  （含调试输出）。

安全措施：非本机来源（remote_addr 非 127.0.0.1 / ::1 / localhost）一律返回 404；
POST 须携带 HMAC 签名的短时表单令牌（10 分钟有效）防 CSRF；跨站请求（Sec-Fetch-Site 为
cross-site）直接拒绝。**若部署在同机反向代理之后，必须在代理层拦截该路径**，否则
remote_addr 恒为回环地址，本机限制失效。

## 二、认证与两步验证（OTP）

登录强制"密码 + TOTP 动态验证码"两步：

1. `POST /api/auth/token`（OAuth2 Password 风格，`password` 字段携带浏览器端 SHA-256 摘要）：
   密码校验通过后返回 10 分钟有效的 `otp_ticket`（JWT，role=`otp_pending`）；
   若该账号在当前设备浏览器或可信来源 IP 上处于 OTP 信任期内（3 天，见下），则直接返回正式 JWT。
   同一账号密码连续失败会被限速（默认 5 次/分钟、20 次/小时，超限 429 + Retry-After）。
2. `POST /api/auth/token/verify`（otp_ticket + 6 位验证码）：校验通过后签发正式 JWT
   （HS256，有效期 12 小时，Bearer 使用），并写入设备信任记录、下发 HttpOnly+Secure 设备 Cookie。
   同一 otp_ticket 连续输错 5 次即作废；同一账号验证码失败 10 次/分钟触发 429。

- 学生未绑定 OTP 时，密码通过后系统自动生成 OTP 并把二维码发到其学号邮箱；
  管理员未绑定 OTP 时拒绝登录（system 提示去本机维护页，普通管理员提示找系统管理员重置）。
- 邮箱验证码（注册/忘记密码）：6 位数字，10 分钟有效，最多尝试 5 次；发送频率受限
  （注册 10 分钟 3 次/IP+学号；忘记密码 10 分钟 3 次）。忘记密码对不存在的学号返回统一提示，
  防止枚举。
- 信任设备：OTP 验证成功后记录来源 IP 与设备 Cookie（SHA-256 哈希入库），3 天内同设备浏览器
  （或同一真实来源 IP）登录第一步直接发令牌，免 OTP。**回环地址（127.0.0.1/::1）不作为信任
  锚点**：生产部署中 tls_proxy 字节转发后应用看到的来源恒为回环，信任它等于信任所有来源。
- 令牌吊销：JWT 携带 `tv`（token_version）声明，校验时与账号当前值比对；改密、管理员重置
  密码、找回密码、维护台重置 system 密码、登出时版本 +1，旧令牌立即失效，同时清空该账号的
  信任设备记录（OTP 重置/重绑路径同样清空）。
- 初始密码：管理员创建学生/管理员或批量导入未填密码时，系统生成随机初始密码（仅当次响应
  可见），账号带 `password_reset_required` 标记；该账号登录后只能访问改密/登出接口，
  前端弹出不可跳过的改密对话框，改密成功后重新登录。
- OTP 绑定/重置统一遵循"验证才生效"：系统只签发含候选密钥（Fernet 加密）的 10 分钟待生效
  票据，用户扫码并输入验证码确认后候选密钥才写入账号；中途放弃一切不变。
  具体场景：学生注册/忘记密码后弹窗重绑（可跳过）、学生主动重置、管理员创建时一次性下发、
  系统管理员两步重置管理员 OTP、本机维护页重置 system OTP。
- 密码存储：浏览器发送 SHA-256 摘要，服务端对摘要做 PBKDF2（600k 轮）哈希存储；
  OTP 密钥与 SMTP 密码用 `SECRET_KEY` 派生的 Fernet 密钥加密存储。

## 三、权限管理

### 3.1 角色

| 角色 | 标识 | 说明 |
| --- | --- | --- |
| 学生 | `user_type=student` | 学号（纯数字）登录，只能操作自己的数据 |
| 部门管理员 | `role=admin` | 拥有 `department` 字段；活动权限见下 |
| 系统管理员 | `role=system_admin` | 仅内置账号 `system`，全权 |

### 3.2 活动级权限模型

- 活动有 `created_by`（创建者管理员，可空）与 `allowed_editors`（可编辑管理员列表，
  `ActivityAllowedEditor` 关联表，有序）。
- 判断规则（`backend/services/permissions.py`）：`system_admin` 恒有权；否则仅当登录账号
  在该活动的 `allowed_editors` 中才有编辑权。
- 新建活动时创建者自动成为唯一编辑者；修改 `department` / `allowed_editors` 仅系统管理员
  可以；删除活动要求编辑权限。
- 删除管理员时清理其全部活动编辑授权，其创建的活动 `created_by` 置空（不删除活动）。
- 问卷权限：绑定活动的问卷与活动同权（编辑者即可管理）；独立问卷（`activity_id` 为空）
  仅系统管理员可创建/管理。
- 反馈的核定录入要求对目标活动有编辑权限。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| admin_id | String(100)，主键 | 账号；`system` 为内置系统管理员 |
| password_hash | String(255)，非空 | PBKDF2 哈希 |
| role | String(20)，非空，默认 admin | `admin` / `system_admin`（CHECK 约束） |

`name` String(100) 主键；`required_credits` Float 非空（类别达标所需学分）；
`position` Integer 非空（展示顺序）。被活动或条目引用时不可删除。

### 4.4 departments（部门）

`id` Integer 自增主键；`name` String(100) 非空唯一；`position` Integer 非空。

### 4.5 settings（系统设置）

`key` String(100) 主键；`value` Text 非空。已知键：

- `total_required_credits`：总学分达标要求。
- `missing_feedback_open`：`"1"` 表示开启集中活动反馈（学生可提交漏录申请）。

### 4.6 email_config（邮件配置，单行表 id=1）

`service_email` 服务邮箱；`service_email_password_encrypted` Fernet 加密的 SMTP 密码；
`student_email_suffix` 学生邮箱后缀（学号 + 后缀即学生邮箱）。

### 4.7 email_verifications（注册/重置邮箱验证码）

`student_id` 主键；`code_hash` 验证码哈希；`expires_at` 过期时间；`attempts` 已尝试次数；
`created_at` 创建时间。

### 4.8 trusted_devices（OTP 信任设备）

`id` 自增主键；`user_type`（student/admin）；`account_id`；`token_hash`（设备 Cookie 的
SHA-256）；`ip`（回环地址存空串，不参与信任匹配）；`created_at`；`expires_at`（3 天）。
登录第一步满足"同设备 Cookie 或同真实来源 IP"且未过期即免 OTP。

### 4.9 activities（活动）

| 字段 | 说明 |
| --- | --- |
| activity_id | String(36) UUID 主键 |
| name | String(200) 非空，索引，唯一（重名不可创建） |
| department | String(100) 非空 |
| created_by | 创建者 admin_id，可空（外键 admins） |
| has_questionnaire | 是否有进行中的报名问卷（由问卷同步，只读） |
| questionnaire_start / questionnaire_end | 报名窗口（由问卷同步） |
| max_participants | 名额，0 表示不限（由问卷同步） |

### 4.10 records（记录）

`record_id` String(36) UUID 主键；`activity_id` 非空（外键，级联删除，索引）；
`record_name` String(200) 非空；`position` 顺序。记录类别经 `record_categories`

## 五、智能学分分配算法

实现位于 `backend/services/credits.py`（`calculate_student_credits` +
`find_best_category_assignment`），刻意保持旧系统 `app.py` 的 DFS 语义。

### 5.1 数据准备

- 按 `Activity.position`、`Record.position` 的持久化插入顺序取出全部记录与条目；
  取目标学生的所有条目，过滤掉类别已不存在（不在 categories 表）的条目。
- 没有有效条目时直接返回全 0 状态。

### 5.2 分配目标

一条目的类别是候选集合，算法为每条目选一个类别（或不选——实现中只遍历候选类别，等价于
每条目必须归入其一），使得**达标（学分 ≥ 类别要求）的类别数量最大化**。

### 5.3 DFS 流程与剪枝

1. 逐条目递归尝试其候选类别；进入下一层前更新该类别累计学分。
2. **可行性剪枝**：剩余条目数 + 当前已达标的类别数 ≤ 历史最优达标数时，整棵子树剪枝
   （`current_qualified + remaining <= best`）。
3. **候选排序**：每个条目的候选类别按 `(该类别是否已达标, -当前累计学分)` 排序——优先尝试
   已达标类别（保持达标）和学分接近要求的类别，更快逼近最优。
4. 叶子节点统计达标类别数，优于历史最优则记录当前分配。

### 5.4 结果

- 总学分 = 全部条目学分之和；类别学分 = 最优分配下各条目学分之和。
- `total_qualified`：总学分 ≥ `total_required_credits`；
  `all_categories_qualified`：每个类别都达标；
  `final_qualified = total_qualified and all_categories_qualified`（**总学分与所有类别要求
  都满足才最终合格**）。
- 返回每条目的 `assigned_category` 供前端展示分配明细。

复杂度为指数级（每条目候选类别数分支），依赖剪枝与候选排序控制实际开销；学生条目数量级
较小时可接受。

## 六、问卷与报名

### 6.1 问卷类型

- **活动报名问卷**：绑定活动（且可选绑定该活动的某条记录）。同一活动最多一个进行中的
  问卷；创建/更新后自动同步活动的 `has_questionnaire`、报名窗口与名额。
- **独立问卷**：`activity_id` 为空，不绑定活动，仅系统管理员可创建/管理。

### 6.2 题目

- **意向类别题**：由绑定记录的类别自动生成——多类别时出单选题（缺省"无"），单一类别
  自动归入无需作答。
- **自定义题目**（类型以 `frontend/src/lib/questions.ts` 为准）：
  - `single_choice` / `multiple_choice`：选项 ≥2 且不重复；支持"其他"自定义项（`其他：` 前缀）。
  - `text`（旧 `textarea` 等同 text + 多行）：可设最大长度（默认 500）、多行；格式校验
    `none` / `phone` / `email` / `idcard` / `regex`（自定义正则）。
  - `number`：可设最小/最大值。
  - `date`：`YYYY-MM-DD`。
  - `rating`：1 至 `max_rating`（2-10，默认 5）。
  - `description`（说明文字）仅存于旧数据，新模板用文字段落替代。
- **正文文档**：题目嵌入文字流（段落数组，text/question 片段混排），旧模板读取时按题目
  顺序自动合成。可插入信息槽位：姓名、学号、手机号、微信号、活动名称、记录名称、意向类别。
- **版本与快照**：标题/题目/正文/绑定记录修改时 `version` +1；提交记录保存 `template_snapshot`
  与 `template_version`，模板后续修改不影响历史提交；导出按当前模板与全部快照的题目并集
  生成答案列。

### 6.3 报名与候补

- 学生在报名窗口内提交；手机号与微信号取自学生档案（未填不允许报名）。取消后允许重新
  提交（覆盖原响应，排名按新提交时间）。
- **候补机制**：`max_participants > 0` 时按提交顺序（`submit_time`，同刻按自增主键）排名，
  超出名额即为候补，不拒绝提交；`absent` 的报名不占名额，候补按顺序自动转正。
- 报名可修改（意向类别、自定义答案），已取消的不可改。

### 6.4 现场签到

- 管理员开启签到后，为每位未签到的有效报名者分配独立的 6 位一次性签到码（候补默认不发，
  由管理员逐人生成）；关闭签到时作废全部未使用的码。
- 学生输入本人报名对应的码签到，码正确即生效并立即作废；签到码只出现在管理端（防远程代签）。
- 管理员可确认签到（候补待确认转正）、直接代签、取消签到（签到仍开启时补发新码）、
  标记/取消缺席（缺席须先取消签到；取消缺席后候补自动转正）。
- `checked_in_missing`：管理员可按记录查看"已签到有效但尚未录入条目"的学生，方便对照录入。

## 七、反馈系统

### 7.1 BUG 反馈（常驻）

- 每人只维护一条 `pending` 状态的 BUG 反馈；已有待处理反馈时提交会被引导为修改原反馈。
- 只能修改仍处于 `pending` 的自己的 BUG 反馈；正文最长 2000 字。
- 管理员回复即结案。

### 7.2 活动漏录反馈（集中活动反馈）

- 仅当管理员开启集中活动反馈（Setting 键 `missing_feedback_open`）时学生可提交。
- 必填：活动名（可选自已有活动或手填）、学分（>0）、至少一个有效类别；记录名可选，
  参与证据可选。
- 选了已有活动的记录时，类别必须 ⊆ 该记录的可行类别；活动不存在时手填活动名且不填记录。
- 提交时按字符集合 Jaccard 相似度（去空白）与已有活动名匹配，返回前 3 个重合率 ≥0.2 的
  提示供填写参考。

### 7.3 管理员处理（action）

- `reply`：回复 BUG 反馈并结案（漏录须走记录或拒绝）。
- `record`：核定并录入（adjustment + reply 必填）。核定值可与学生申请不同：
  - 活动不存在时自动创建（处理人为创建者并自动获得编辑权限）；无编辑权限时报错。
  - 记录不存在时在该活动下自动创建（类别取核定类别）；记录已存在时核定类别必须 ⊆ 记录
    可行类别。
  - **完全相同条目（同学号、同学分、同类别集合）已存在时不重复录入**。
  - 自动录入的 `entry_id` 存入 `adjustment`，取消核定时自动删除该条目（条目被人工改过
    则不删，提示人工核对）。
- `reject`：拒绝漏录申请（reply 必填）。
- `reopen`：重新打开（回到 pending，清空结案信息；已记录的自动删除对应条目）。

反馈列表待处理优先（先报先处理），已处理按时间倒序；所有管理员可见可处理。

## 八、导出

- Excel 一律用 openpyxl（xlsx）；`xlsx_file_response` 统一封装响应。
- 导出端点：
  - `GET /api/admin/students/info/export`：学生报名信息（学号/姓名/手机号/微信号/建议/更新时间），系统管理员。
  - `GET /api/admin/export`：学生学分统计（总学分、各类别学分与合格、最终合格），系统管理员。
  - `GET /api/admin/questionnaire/responses/<id>/export`：单问卷填写记录（排名/基本信息/状态/版本/签到 + 每题一列），问卷管理员。
  - `GET /api/admin/questionnaires/export`：全部问卷填写记录汇总，系统管理员。
- 前端页面（如学分报告）另有浏览器端 PDF/CSV 生成；CSV 使用 UTF-8 BOM 以保证中文 Excel
  兼容。
- 学生 CSV 导出不含密码列（密码已改为哈希存储）。

## 十、运行与部署要点

- 开发：`uv sync` 安装依赖；`cp .env.example .env` 配置 `SECRET_KEY`；首次启动自动创建
  内置 system 账号（随机密码不落盘、不打印），随后在本机访问 `/local/system` 完成初始化；
  `uv run python run.py` 启动开发服务器（端口 5000）；前端 `cd frontend && npm run build`
  后由 Flask 托管，`npm run dev` 为 Vite 开发模式（5173，/api 代理到 5000）。
- 生产：`start_server.bat` / `start_server.sh`（Waitress）。`deploy_server.py` 启动前自动
  检查 `instance/tls.crt` / `tls.key`，不存在则以 `gen_cert.ensure_cert()` 生成自签名证书
  （SAN 含 localhost 与本机内网 IP），随后用 **cheroot** 提供 HTTPS（端口不变）；生成失败
  才回退明文 HTTP。可用 `uv run python gen_cert.py --force` 重签。
- 必须设置强随机 `SECRET_KEY`（生产缺省拒绝启动）。浏览器发送的是密码的 SHA-256 摘要，
  生产由 tls_proxy 统一对外：localhost 一律 HTTP、LAN 一律 HTTPS（拒绝外部明文 HTTP）。更换 `SECRET_KEY` 会使已加密的 SMTP 密码与 OTP
  待生效票据失效。
- 数据库：SQLite（`instance/` 下），WAL 模式、`busy_timeout`、`foreign_keys=ON`，
  事务写入。测试：`uv run pytest`。
